# Capability, Architecture & Build Dashboard

`docs/dashboard.html` is the LoanOS India founder control dashboard: a branded,
repository-backed view of overall maturity, current constraints, owner/persona
lanes, product planes, the complete capability register, evidence drill-down,
recent commits, backlog epics, and the latest test result. It is generated by
[`scripts/build-dashboard.mjs`](../scripts/build-dashboard.mjs) and regenerated
automatically on every `./loanos.sh build`.

The design assumes one accountable product-company founder who operates through
multiple specialist personas and delegates bounded work to AI agents. It does
not invent agent activity. Instead, every capability can produce an agent-ready
work packet containing its owner persona, acceptance rule, remaining scope,
dependencies, existing evidence and source digest. The human remains responsible
for reviewing proof and promoting catalogue maturity.

## How to regenerate

| Command | Behaviour |
| --- | --- |
| `./loanos.sh build` | Runs the full build + `npm test`, syncs and validates the trace register, regenerates the dashboard using that same test run, validates the artifacts, and fails if any dashboard stage fails. |
| `./loanos.sh dashboard` | Runs the synchronized, validated dashboard pipeline with a live test run. |
| `npm run dashboard` | Same dashboard pipeline, without the shell wrapper. |
| `npm run dashboard:watch` | Performs an initial full dashboard build, then watches relevant repository sources and reruns the pipeline after debounced changes. |
| `npm run dashboard:check` | Validates committed JSON/HTML artifacts against current sources without regenerating or rerunning tests. This is the CI freshness gate. |
| `npm run trace:sync` | Syncs `docs/product/capability-trace.json` only (no dashboard). |
| `npm run trace:validate` | Validates evidence files, metadata, status-specific proof, and non-decreasing coverage floors. |
| `node scripts/build-dashboard.mjs` | Direct invocation after trace synchronization. Set `DASHBOARD_TEST_LOG=<file>` to parse an existing test log instead of running tests. |

Outputs written on each run:

- `docs/dashboard.html` — the rendered dashboard (open directly or through the canonical `/status/` application route).
- `docs/dashboard-data.json` — the same data as JSON, for reuse elsewhere.

Both are build artifacts; edit source documents and implementation evidence, not
these files. Writes are atomic per artifact so an interrupted render does not
leave a partially written page.

The portal link is labelled **Build status** deliberately: this dashboard reports repository capability, architecture, evidence, test and journey-readiness state. It is not a production uptime page and does not establish tenant or journey production readiness.

## Live and offline behaviour

The word *live* is used narrowly:

- when served over HTTP, the page fetches `dashboard-data.json` every 30 seconds
  with `cache: no-store`, shows the active sync state, and cache-busts/reloads when
  a new snapshot ID appears;
- `npm run dashboard:watch` keeps that JSON/HTML pair regenerated as repository
  sources change;
- when opened through `file://`, browser fetch restrictions prevent polling, so
  the page explicitly labels itself an **offline repository snapshot** and uses
  its embedded data;
- the generated timestamp, source digest, Git SHA, dirty-worktree count and test
  source make snapshot age and provenance visible.

This is live repository status, not production runtime telemetry. The engineering
and operational-readiness panel derives its signals from the test result,
capability/evidence registers, journey-depth audit, architecture freshness and
Git worktree. Production loan, queue, provider, SLO, incident and control data
belongs in authenticated tenant/platform workspaces with tenant isolation, not
in this documentation artifact. The dashboard says `not_connected` for runtime
telemetry rather than implying that an absent signal is healthy.

## Solo-founder drill-down model

The page is ordered for progressive decisions:

1. **Executive snapshot** — maturity, evidence integrity, tests and worktree state.
2. **Whole-system map** — the governed seven-layer architecture SVG, embedded into
   the generated page with source/digest lineage.
3. **Engineering and operational readiness** — build health, evidence integrity,
   journey readiness, diagram freshness and a deterministic issue queue, plus an
   explicit boundary around live runtime telemetry.
4. **Founder operating desk** — a deterministic constraint queue plus owner/persona
   lanes. Queue order is restrictive status then capability ID, not inferred
   commercial priority.
5. **Product planes** — LOS, LMS, LWS, Compliance OS and supporting-plane rollups.
6. **Evidence explorer** — status, plane and owner filters plus full-text search
   over names, acceptance, gaps, dependencies and evidence.
7. **Agent handoff** — copy a bounded Markdown work packet from any capability;
   the agent proposes work and verification, while the human decides completion.
8. **Lineage** — exact sources, test accounting, source digest and Git state.

## Data sources

Everything on the dashboard is derived at generation time from the repository —
nothing is hand-maintained in the HTML:

| Panel | Source |
| --- | --- |
| Capability register, category status, plane rollups | `docs/product/complete-system-capability-catalog.md` (Detailed Capability Register tables) |
| Owner/persona lanes, acceptance, remaining scope, dependencies, evidence | `docs/product/capability-trace.json` |
| Product-plane grouping | The shared mapping in `scripts/planes.mjs` (`PLANE`), derived from `docs/product/what-we-are-building.md` |
| Backlog epics | `docs/product/build-backlog.md` (`## Epic` headings + `Status:` lines) |
| Whole-system architecture | `docs/architecture/loanos-system-map.json` plus its checked generated SVG |
| Journey readiness | `docs/product/product-journey-platform-depth.json` (production-ready remains explicitly zero until governed external/institution evidence exists) |
| Engineering/readiness issue queue | Derived from tests, capability statuses, evidence integrity, journey depth and Git state; never hand-maintained in HTML |
| Commits, branch, SHA, dirty state | `git log`, `git rev-list`, `git status` |
| Test suite | Live `node --test tests/*.test.js` run (or a reused build log) |
| Brand system | `docs/gtm/brand/brand-guide.md` and the approved `apps/web/assets/loanos-logo-mark.png` |

The shared parser accepts the catalogue's two- and three-letter capability
prefixes, including the complete `UX-*` experience family. Automated checks
compare the catalogue's declared snapshot with every parsed row and fail if a
category, capability, plane mapping or unique ID silently drops out.

Because status comes straight from the catalogue's `Status` column, the
dashboard is only as accurate as that table. Keeping capability statuses honest
as code lands is what keeps this view trustworthy — see the catalogue's own
governance rules.

## Capability trace register

`docs/product/capability-trace.json` is the machine-trackable register the
catalogue's "Next Maintenance Step" calls for: one entry per capability ID, so
every capability can be traced to the evidence that proves it. In the dashboard,
clicking any capability row expands its trace panel.

Each entry:

```json
"OFR-004": {
  "capability": "KFS unique proposal, validity, APR sheet, and amortisation schedule",
  "category": "12. Offers, KFS, Sanction, and Contracting",
  "plane": "LOS",
  "applicability": "Core",
  "status": "Implemented",
  "owner": "Lending Product & Compliance",
  "evidence": [
    { "type": "endpoint", "ref": "POST /kfs", "note": "KFS generation" },
    { "type": "test", "ref": "tests/compliance.test.js:216", "note": "KFS must include RBI-required lending disclosures" }
  ],
  "acceptance": "A checksum-bound KFS is generated and its regulatory fields are executable-test covered.",
  "dependencies": [],
  "notes": "Implemented scope is evidenced; provider delivery remains separately governed.",
  "lastReviewed": "2026-07-15"
}
```

**Derived vs curated fields.** `capability`, `category`, `plane`,
`applicability`, and `status` are *derived* — re-synced from the catalogue on
every run (the catalogue stays the source of truth for status). `owner`,
`evidence`, `acceptance`, `dependencies`, `notes`, and `lastReviewed` are
*curated* — filled in by hand and **preserved across every sync**. Adding a
capability to the catalogue adds a blank entry here automatically; removing one
keeps the entry and flags it `"orphaned": true` so curation is never lost.

**Evidence types.** `test`, `endpoint`, `code`, `doc`. A `ref` that looks like a
repo-relative file path (optionally with `:line`) renders as a link in the
dashboard; `endpoint` refs render as a method+path badge.

**To trace a capability**, open `capability-trace.json`, find its ID, and add
evidence rows pointing at the tests, endpoints, code, and docs that implement it.
Run `npm run trace:validate` before regeneration. CI requires every current entry
to retain linked evidence and every `Implemented` entry to retain both executable
test evidence and code or endpoint evidence. Policy floors must exactly match the
current catalogue and may never decrease. The dashboard calls this
integrity-checked evidence coverage; it is not the same as product completion.

## Catalogue maturity score

Each capability's status is normalised to one of:
`Implemented`, `Partial`, `Partial/Mock`, `Mock`, `Missing`, `Partner`,
`External`. The weighted catalogue-maturity percentage for a category or plane is:

```
maturity = sum(weight[status]) / count(scored capabilities)
```

with weights `Implemented=1.0`, `Partial=0.4`, `Partial/Mock=0.4`, `Mock=0.3`,
`Missing=0`. `Partner` and `External` capabilities are excluded from the
denominator (they are provider/policy obligations, not internal build work).
This is a planning indicator based on curated statuses, not an independent claim
of production readiness. Weights live in `scripts/dashboard-utils.mjs`.

### Known cross-plane judgement calls

A few categories legitimately straddle planes; the current assignment picks the
dominant one. If the team disagrees, change the number in the `PLANE` map and
update the table above:

- **6 Consent/Privacy** → Compliance OS (consent *capture* is an origination
  step, but the ledger and data-principal rights are ongoing compliance).
- **8 Fraud/Identity Risk** → LWS (application-time fraud is origination, but the
  fraud case + natural-justice workflow is workflow-driven).
- **11 Collateral/Security** → LOS (perfection at origination, though the CERSAI
  lifecycle continues into LMS).

## Maintenance

The dashboard regenerates from source on `./loanos.sh build`. Five things keep
it correct:

1. Update a capability's `Status` in the capability catalogue when its real state
   changes (this is already required by the catalogue's Definition of Done).
2. When adding or renaming a catalogue category, add its number to the `PLANE`
   map in the generator and to the mapping table above.
3. Add owner, acceptance, dependencies, remaining-gap notes and real evidence
   for every new capability, then raise—never lower—the floors in
   `capability-evidence-policy.json` when the catalogue grows.
4. Run `npm run dashboard:watch` for a continuously refreshed local view, and
   serve the repository over HTTP so browser polling is active.
5. Edit the architecture model, regenerate the SVG, and visually inspect both
   the standalone image and its embedded desktop/mobile dashboard layout.
6. Keep the canonical brand guide, generator tokens and approved mark aligned;
   `npm run dashboard:check` enforces the critical brand/live-control contract.
